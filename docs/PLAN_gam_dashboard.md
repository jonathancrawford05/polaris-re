# Plan: the HGAM fitter in the dashboard (read-only first), then every surface

> **STATUS: PROPOSED 2026-10-21 (maintainer direction after PR #275 merged); becomes the ACTIVE EPIC when the PR that adds it merges.** Slice order is fixed (§4). **The epic-start session writes this epic's ADR (next free number) and `CONTINUATION_gam_dashboard.md` (status IN PROGRESS), then takes slice D1.** The readiness epic (`PLAN_gam_real_data_readiness.md`, R1-R4) is merged and has no open slice.

**Source:** maintainer, 2026-10-21: *"the next valuable epic gets our HGAM into the dashboard and then I can see how it holds up in practice and we can expose it to all surfaces"*; host = the existing experience-improvement page; read-only first; default `bam` above 300k rows/cells, selectable at any size, with runtime and memory warnings from the selection and the input size.
**Routine:** `ROUTINE_MGCV_PARITY.md`. This epic is not a parity epic: its slices ship a capability whose numbers come from `polaris_re.gam`, which is already verified against `mgcv` (ADR-258/260/261). So the ADR-193 rule is applied to what is NEW: any comparison a slice reports must still name two independent producers, and a number the page shows that Polaris computes alone is labelled MEASUREMENT (own criterion), never parity.

## 2. Definition of done
A maintainer can, in the existing experience-improvement page and with data they load themselves: choose a formula from the verified subset, choose `gam` or `bam` (default by size, §3), read the runtime and memory warning BEFORE the run, run the fit, and see the fitted effects, `edf`, convergence flags and `summary()`; an unsupported formula shows the refusal message by name; nothing the page shows feeds pricing. All tests run without real data.

## 3. Decisions (maintainer, 2026-10-21; do not re-ask)
1. Host: the existing page. 2. Read-only first slice; Anchor 7 holds for the CLI, MCP and API, lifted for the dashboard only. 3. Default `gam` at or below **300,000 cells/rows**, `bam` above; the user may select either at any size. 4. Warn before the run from the selection and the input size: runtime, memory, and (for `bam`) that smoothing parameters come from a different algorithm. 5. Estimates come from a **measured model** (Polaris `gam` memory has to be MEASURED in D1, or reported as unmeasured; it must not be inferred from the oracle's container limit) (the R2/R3 profile tables, with the machine described), never a guess; a request the machine cannot hold is warned loudly and not silently attempted. 6. `bam` unsupported combinations (family, `tp`) are stated, never silently replaced by `gam`. 7. Data is only what the user loads; none in the repo or the cloud.

## 4. The slices (each ships a user-visible capability; no splitting without a maintainer comment)
- **D1 — fit and display, read-only.** A "GAM (HGAM fitter)" section on the existing page: formula input with the verified-subset help text and refusal messages, family choice, engine choice with the §3 default, the pre-run warning from a measured cost model, the fit, the effects/edf/convergence/`summary()` display. Comparison/evidence: the page's numbers are `polaris_re.gam`'s (already INDEPENDENT-verified); D1's own checks are MEASUREMENT (own criterion): the cost model is validated against the committed R2/R3 timings (predicted vs measured, reported, with the tolerance derived before the first run), and a UI test asserts the warning text for each engine x size cell. **Release condition:** none; first slice.
- **D2 — the fit as an input to the page's A/E or improvement views** (the deferred alternative to read-only). Written at D2's start from what the maintainer saw in D1. **Release condition:** the maintainer's use of D1 and a written go.
- **D3 — other surfaces** (CLI, MCP, API). **Release condition:** the maintainer's written go after D2; Anchor 7 stays until then.

## 5. Rules that keep this epic from spiralling
1. One slice per session; D2 and D3 are not started without their release condition. 2. No solver work, no new start strategy (the outer search is closed; Newton is the default). 3. No new `mgcv` constructs: a formula the verified subset refuses stays refused, with its message. 4. A number the page shows without a second producer is labelled MEASUREMENT, not parity. 5. The cost model is measured, labelled with the machine it was measured on, and refuses to extrapolate beyond the measured range without saying so. 6. Real data never enters the repo or the cloud. 7. Existing pages' behaviour and the goldens (`tests/qa/golden_outputs/`) stay unchanged; the new section is additive. 8. Questions go to the maintainer the session they arise (PR body + CONTINUATION), with a recommended answer.

## 6. Risks, in the order they are likely to bite
1. The page's fit machinery today is the older experience GAM; adding a second engine to one page without confusing which numbers are which (label every number with its engine). 2. The cost model is built from one maintainer machine's profile; it must say so and widen its stated uncertainty off that machine. 3. Streamlit rerun semantics: a multi-minute fit must not re-execute on each widget change (cache by a fit signature, as `_cached_fit_models` does). 4. Memory: a `gam` request near the ceiling can take the dashboard process down; the warning is mandatory and the run is explicit, not automatic.
